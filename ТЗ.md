# ТЕХНІЧНЕ ЗАВДАННЯ (ТЗ)

**Проєкт:** Модульний кросплатформений фреймворк-калькулятор (Modular Calculator Framework)  
**Версія документа:** 1.0 (MVP)  

---

## 1. Вступ

### 1.1. Мета проєкту
Розробити розширюваний програмний комплекс для математичних обчислень. Система повинна базуватися на архітектурі компілятора (транслятор + віртуальна машина) і підтримувати заміну або додавання компонентів (лексерів, парсерів, математичних функцій) за допомогою динамічних бібліотек без перекомпіляції ядра.

### 1.2. Глосарій
* **Ядро (Core)** — базова статична або динамічна бібліотека, що містить інтерфейси, віртуальну машину та загальну логіку.
* **Плагін (Модуль)** — динамічна бібліотека (`.dll` або `.so`), створена користувачем або розробником, що реалізує специфічні інтерфейси (наприклад, синтаксис).
* **Хост (Host/CLI)** — кінцева програма користувача (консольна або графічна), яка завантажує плагіни та взаємодіє з ядром.
* **AST (Абстрактне синтаксичне дерево)** — внутрішнє представлення математичного виразу в пам'яті.
* **VM (Віртуальна машина)** — стекова машина всередині Ядра, яка виконує згенерований байт-код.

---

## 2. Технологічний стек та оточення

* **Мова програмування:** C++ (стандарт C++17 та вище).
* **Система збірки:** CMake / Ninja (поділ на мінімум 3 таргети: `core`, `plugin`, `executable`).
* **Платформи:** Linux (GCC / Clang), Windows (MSVC / MinGW). У пріоритеті Linux
* **Формат плагінів:** `.dll` (Windows), `.so` (Linux).
* **Тестування:** Модульні тести для ізольованих компонентів.

---

## 3. Архітектура системи

Система повинна складатися з трьох незалежних рівнів.

### 3.1. Ядро (Core Framework)
* Містить визначення чистих віртуальних інтерфейсів: `ILexer`, `IParser`, `IASTNode`, `IVirtualMachine`, `ICompiler`.
* Містить реалізацію стекової Віртуальної машини (обчислювального рушія).
* Містить підсистему кросплатформеного завантаження модулів (обгортка над ОС-специфічними командами завантаження динамічних бібліотек).

> **Важливо:** Ядро не знає про конкретний синтаксис (стандартний чи польський запис), воно лише вміє працювати з готовим AST і байт-кодом.

### 3.2. Система плагінів (Plugins)
* Плагін є незалежною бібліотекою, яка компілюється окремо від Ядра.
* Плагін реалізує етап "Фронтенду" (перетворення тексту в AST).
* Кожен плагін експортує заздалегідь відому C-функцію (точку входу), наприклад `InitPlugin`, яка повертає фабрику для створення об'єктів лексера і парсера.

### 3.3. Хост-додаток (CLI)
* Надає інтерфейс командного рядка (REPL — Read-Eval-Print Loop).
* Сканує директорію `plugins/` під час запуску.
* Зв'язує завантажений плагін з Ядром та передає туди ввід користувача.

## 4. Вимоги до інтерфейсів (ABI та безпека)

Оскільки Ядро та Плагіни можуть бути зібрані в різний час і різними компіляторами, висуваються жорсткі вимоги до їхньої взаємодії:

* **Керування пам'яттю:** Об'єкт, створений усередині динамічної бібліотеки (наприклад, вузол дерева), повинен бути знищений методами цієї ж бібліотеки. Забороняється пряме видалення об'єктів плагіна механізмами Ядра.
* **Обмін даними:** Передача даних між Ядром і Плагіном має здійснюватися через базові типи (числа, вказівники), C-подібні структури або спеціально спроєктовані безпечні обгортки. Передача стандартних контейнерів (наприклад, `std::string` або `std::vector`) по значенню через межу `.dll`/`.so` заборонена для уникнення збоїв (ABI Incompatibility).
* **Обробка помилок:** Винятки (Exceptions), згенеровані всередині плагіна, не повинні перетинати межу `.dll`/`.so`. Плагін повинен перехоплювати їх самостійно і повертати в Ядро код помилки або об'єкт статусу.

## 5. Граматика стандартного модуля (MVP)

Хоча Ядро системи є синтаксично-незалежним, для Мінімально Життєздатного Продукту (MVP) розробляється стандартний плагін класичної побктовго калькулятора. 
Нижче наведено його граматику у форматі EBNF, яка визначає пріоритет операцій та буде реалізована в Парсері методом рекурсивного спуску.

```ebnf
Expression  ::= Term { ( "+" | "-" ) Term }
Term        ::= Power { ("/" | "*" | "mod") Power }
Power       ::= Factor [ "^" Power ]
Factor      ::= [ "+" | "-" ] Prim [ "%" ]
Prim        ::= Identifier | Number | "(" Expression ")" | FuncCall
FuncCall    ::= Identifier "(" [ Expression { "," Expression } ] ")"
Identifier  ::= ( "_" | alpha ) { "_" | alpha | digit }
Number      ::= ( digit { digit } [.] { digit } ) | ( { digit } [.] { digit } digit ) 
alpha       ::= "a" | "b" | "c" | ... | "z"
digit       ::= "0" | "1" | "2" | ... | "9"
```

## 6. Беклог та Ідеї на майбутнє (Out of Scope for MVP)

*   **Просунутий Data-Driven Лексер:** 
    Створення універсального рушія лексичного аналізу всередині Ядра. Замість написання коду розбору (callbacks), розробник плагіна передаватиме лише масив конфігураційних правил.
    *   *Архітектура правила:* Клас/структура типу "Tagged Union", яка містить тип збігу (Exact, Regex, Built-in) та відповідні дані (рядок, патерн або вказівник на функцію).
    *   *Переваги:* Максимальне спрощення створення нових синтаксичних плагінів.
