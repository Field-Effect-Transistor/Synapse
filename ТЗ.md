# ТЕХНІЧНЕ ЗАВДАННЯ (ТЗ)

**Проєкт:** Модульний кросплатформений фреймворк-калькулятор (Modular Calculator Framework)  
**Версія документа:** 1.1 (MVP)  

---

## 1. Вступ

### 1.1. Мета проєкту
Розробити розширюваний програмний комплекс для математичних обчислень. Система повинна базуватися на архітектурі транслятора (лексер + парсер + інтерпретатор/віртуальна машина) і підтримувати заміну або додавання компонентів (синтаксису, математичних функцій, типів даних) за допомогою динамічних бібліотек без перекомпіляції ядра.

### 1.2. Глосарій
* **Ядро (Core)** — базова бібліотека, що містить інтерфейси, структуру AST, патерни обходу та загальну логіку керування модулями.
* **Плагін (Модуль)** — динамічна бібліотека (`.dll` або `.so`), що реалізує специфічні інтерфейси (наприклад, фронтенд для конкретного синтаксису або нові типи даних).
* **Хост (Host/CLI)** — кінцева програма користувача, яка завантажує плагіни та взаємодіє з ядром (REPL).
* **AST (Абстрактне синтаксичне дерево)** — внутрішнє ієрархічне представлення математичного виразу в пам'яті.
* **Visitor (Відвідувач)** — архітектурний патерн, що ізолює алгоритми (обчислення, генерація коду, друк) від самої структури AST.
* **Value** — універсальний ABI-безпечний контейнер (Tagged Union) для передачі даних між вузлами та модулями (числа, логіка, кастомні об'єкти).

---

## 2. Технологічний стек та оточення

* **Мова програмування:** C++ (стандарт C++17 та вище).
* **Система збірки:** CMake / Ninja (поділ на мінімум 3 таргети: `core`, `plugin`, `executable`).
* **Платформи:** Linux (GCC / Clang), Windows (MSVC / MinGW). У пріоритеті Linux.
* **Формат плагінів:** `.dll` (Windows), `.so` (Linux).
* **Тестування та Контроль якості:** GoogleTest (GTest) для модульних тестів, LCOV для звітів про покриття коду, AddressSanitizer (ASan) для контролю витоків пам'яті.

---

## 3. Архітектура системи

Система складається з трьох незалежних рівнів.

### 3.1. Ядро (Core Framework)
* Містить визначення чистих віртуальних інтерфейсів: `ILexer`, `IParser`, `IASTNode`, `IVisitor`, `ICustomValue`.
* Надає власні ABI-безпечні утиліти (наприклад, `Synapse::UniquePtr`, `Synapse::Value`), щоб уникнути конфліктів стандартних бібліотек (STL) між різними компіляторами.
* Містить імплементацію базових алгоритмів обходу дерева (наприклад, `MathEvaluator` або `AstPrinter` на базі патерна Visitor).

> **Важливо:** Ядро не знає про конкретний синтаксис (стандартний чи польський запис), воно лише надає будівельні блоки для AST і механізми їх обходу.

### 3.2. Система плагінів (Plugins)
* Плагін компілюється окремо від Ядра.
* Плагін реалізує етап "Фронтенду" (перетворення тексту в AST за допомогою Лексера і Парсера).
* Плагіни можуть розширювати систему типів Ядра, створюючи об'єкти на базі `ICustomValue` (наприклад, Матриці), пам'ять яких безпечно керується Ядром.

### 3.3. Хост-додаток (CLI)
* Надає інтерфейс командного рядка (REPL — Read-Eval-Print Loop).
* Сканує директорію `plugins/` під час запуску, підключає модулі.
* Зв'язує завантажений плагін з Ядром та передає туди ввід користувача.

## 4. Вимоги до інтерфейсів (ABI та безпека)

Оскільки Ядро та Плагіни можуть бути зібрані в різний час і різними компіляторами, висуваються жорсткі вимоги до їхньої взаємодії:

* **Керування пам'яттю (Custom Deleters):** Об'єкт, створений усередині динамічної бібліотеки (наприклад, вузол дерева або кастомний тип), повинен бути знищений методами цієї ж бібліотеки. Для цього використовується патерн віртуального знищення (`virtual void destroy() = 0`) у комбінації зі смарт-поінтерами Ядра.
* **Обмін даними:** Передача даних між Ядром і Плагіном здійснюється виключно через C-сумісні типи (`const char*`, `size_t`) або власні ABI-безпечні обгортки (`Synapse::Value` як Tagged Union). Передача контейнерів STL по значенню через межу модулів заборонена.
* **Обробка помилок:** Винятки (Exceptions), згенеровані всередині плагіна, не повинні перетинати межу `.dll`/`.so`.

## 5. Граматика стандартного модуля (MVP)


Для Мінімально Життєздатного Продукту (MVP) розробляється стандартний плагін класичного побутового калькулятора. 
Алгоритм синтаксичного аналізу: **Рекурсивний спуск (Recursive Descent)**.
Нижче наведено його граматику у форматі EBNF, яка визначає пріоритет операцій:

```ebnf
Expression  ::= Term { ( "+" | "-" ) Term }
Term        ::= Power { ("/" | "*" | "mod") Power }
Power       ::= Factor [ "^" Power ]
Factor      ::= [ "+" | "-" ] Prim [ "%" ]
Prim        ::= Identifier | Number | "(" Expression ")" | FuncCall
FuncCall    ::= Identifier "(" [ Expression { "," Expression } ] ")"
Identifier  ::= ( "_" | alpha ) { "_" | alpha | digit }
Number      ::= ( digit { digit } [.] { digit } ) | ( { digit } [.] { digit } digit ) 
alpha       ::= "a" | "b" | "c" | ... | "z"
digit       ::= "0" | "1" | "2" | ... | "9"
```

## 6. Беклог та Ідеї на майбутнє (Out of Scope for MVP)

Наступні архітектурні покращення та фічі відкладені до версії 2.0+:

1.  Arena Allocator (Пул пам'яті):
    Відмова від смарт-поінтерів у дереві AST на користь суцільного блоку пам'яті. Збільшить швидкодію створення та обходу дерева на порядки, усуне фрагментацію купи та каскадні деструктори.
2.  Stackless Visitor (Безстековий обхід):
    Переведення алгоритмів обходу AST з глибинної рекурсії на ітеративний обхід із власним стеком (масивом). Це унеможливить падіння програми (Stack Overflow) при генерації екстремально глибоких виразів.
3.  Computer Algebra System (CAS):
    Розширення типу Value підтримкою матриць, векторів та нерозв'язаних змінних. Створення нових Відвідувачів (Visitors) для символьної математики (спрощення рівнянь, перенесення змінних, побудова графіків).
4.  Байт-код та Віртуальна Машина (JIT):
    Створення CompilerVisitor, який компілює AST у компактний байт-код для власної стекової Віртуальної Машини. Це забезпечить максимальну продуктивність для багаторазових обчислень (наприклад, рендеринг графіків функцій).
5.  Pratt Parser (Top-Down Operator Precedence):
    Заміна алгоритму рекурсивного спуску на алгоритм Пратта, що базується на таблиці пріоритетів. Значно спростить процес додавання нових операторів авторами плагінів.
6.  Просунутий Data-Driven Лексер: 
    Створення універсального рушія лексичного аналізу всередині Ядра, який парситиме текст на основі переданого з DLL масиву правил.
